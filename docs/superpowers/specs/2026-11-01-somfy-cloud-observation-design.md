# Somfy cloud observation

## Intent and authorization

Continue the approved local-first TaHoma driver with an optional Somfy cloud complement to retrieve saved scenarios and programming, strictly read-only, tested and easy to carry upstream. User explicitly requested implementation, branches, tests and subagents; no further design approval round is needed for routine choices. This document records implementation decisions, not additional user decisions. Keep the local convergence PR99 unchanged; cloud goes on feature/tahoma-cloud-readonly, based on d81b2be.

## Outcome

A working optional cloud observer in the SAME overkiz driver. It can operate without a local host/token, and coexist with local polling. Owner-only onboarding creates an independent Somfy session, offers explicit site/gateway selection, then retrieves scenarios, calendar days/rules, triggers and scheduled executions. Owner-only UI shows read-only collections and full bounded definitions. No automation import, evaluation, activation, editing, cancellation, physical commands or global logout. House stays read-only. Code and synthetic tests before any account connection; no Home Assistant session/credential extraction. Connection may require the user to enter their Somfy login into the prepared local interface.

## Protocol evidence

Classic endpoint availability on a modern gateway is not guaranteed; represent each collection's outcome independently.

Allow only fixed HTTPS destinations and enum-selected method/path pairs. Somfy network POSTs are ONLY Accounts password grant, Ginaite token exchange and serialized refresh. Read paths on the explicitly selected region: actionGroups; setup/calendar/days; setup/calendar/rules; triggers; exec/schedule; exec/delayedTriggerSchedule. Optional metadata reads setup/location (retain timezone only), setup/devices (retain target URL/label only), setup/gateways (verify selected scope). BOB directory GET is fixed, pages20, max200 sites/candidates; incomplete discovery must not silently select an incomplete first result. No arbitrary host, redirect, cookie login, logout, generic request or actuator method.

GET exec/schedule is read-only; POST variants are prohibited. Scenarios preserve action order, target URLs, command names and typed parameters. Rules preserve priorities/finalRule/references. Triggers preserve effects/conditions and unknown structures as opaque data. No interpreter/recalculated occurrence. utcTime is Unix milliseconds. Calendar hours are native setup wall time; show bounded syntactically plausible provider timezone explicitly unverified, never silently convert with host/browser timezone. DAWN/DUSK remain astronomical labels. Preserve unknown variants with an interpretation warning; do not drop them. A 200 array may be empty; 204/object error/HTML/null is not an empty inventory. ## Bounds and private data

Shared catalogue DTO and validator in moli-overkiz::inventory. Versioned encrypted snapshot cloud_inventory_v1, separate from cloud_session and onboarding records. Hard serialized total1MiB per instance, collection response512KiB, object definition64KiB, depth24, total JSON nodes32768, total top-level inventory entries2048, individual strings8192bytes (labels256), object identifiers256bytes. Overflow rejects the incoming collection without erasing prior good content; do not silently truncate. Validate again on cached API reads, since the generic vault has no bounds. Metadata response bounds512KiB; token bodies64KiB and individual token strings16KiB. Keep structured bodies only for collection data, never headers/token responses. Full targets/parameters/notifications belong in encrypted snapshot and owner-only GET; no raw data in generic device points/SSE/MCP/logs/Debug. No personal data in repository or public PRs. Sources and test fixtures entirely synthetic.

One read-only summary device per configured cloud instance may publish counts, health/freshness and qualification state; all Access.write=false, Semantic::Other, empty members. No cloud physical devices, so native IDs remain unchanged and no duplicates. Reject all commands to reserved cloud IDs before any native preflight, even stale writable metadata and every origin. Keep local read_only=false compatibility default; cloud always read-only independent of it. Our actual pilot configuration uses read_only=true.

## Authentication and session safety

Use current public pyoverkiz application constants with explicit source/version, not user-supplied application secrets. Username/password bootstrap only; no custom OAuth browser callback is assumed supported. Never retain password after consuming onboarding input. API accepts bounded owner-only requests into encrypted pending input; driver is the sole session writer. Add narrow atomic secret take to runtime/vault for consuming that pending input without deleting a concurrent newer request. No generic secret-reading HTTP API. Single active Moli process per data directory, matching existing vault/runtime assumptions; no multi-process token-sharing claim.

Cloud actor owns token lifecycle. Versioned session binds refresh/access/expiry/phase and optional selected scope. Explicit selected setup/site and anchor gateway must come from authenticated BOB candidates; no first-site guess. OAuth scopes the Overkiz setup/siteOID (BOB sub-site externalOID), not an individual gateway. Observe the entire returned selected setup, including multiple gateways; verify anchor membership but never filter opaque programs by device URL. UI explicitly says all gateways of the selected site are included. A parent BOB site with several externalOID setups yields separate choices; deduplicate gateways sharing the same setup without claiming gateway-only isolation. Catalog identity and scope are the setup; gateway is a verified anchor. Unknown country requires explicit supported region selection, never silent EMEA fallback. No bearer sent to a host obtained from provider payload. Persist unscoped session before waiting for selection; preserve candidates privately. Store scoped session after selection. Sessions are independent of HA and local token/cert keys. A new login establishes a new connection generation; manual refresh does not. Catalogs bind instance, connection generation and exact scope. While reconnecting or changing scope, never serve an old catalog as belonging to the new connection; retain it encrypted if useful but return pending until a matching snapshot is present.

Before EVERY refresh, persist a refreshing marker, then send once. After successful rotation retain the new refresh immediately and persist the new session before further authenticated reads. If persistence fails, retry persistence of the new session, never refresh using the old token. Lost response/invalid_grant/refreshing marker on restart requires reconnect; never blind replay. Handle refresh responses retaining a valid new refresh even if other fields are unusable. Access expiry uses monotonic timing while running and conservative persisted expiry on restart; missing expires_in fallback300seconds,5seconds margin, invalid extremes rejected. A GET 401 permits at most one refresh+re-read; 403 isn't assumed expiration. One actor prevents concurrent refresh. Reconnection generations abort/ignore stale actor events and never let an old session overwrite a newer login. No tokens/credentials in error text or Debug.

A new login first persists a fresh-generation bootstrap marker without scope, before sending the password. A bounded public session-binding helper exposes only persisted generation/scope/phase, never tokens. Cached API reads compare this authoritative binding with state/catalogue identity, preventing a stale state-key write or crash from exposing a previous connection as current. Same-identity historical data may remain owner-visible during refresh/auth failure with explicit stale qualification; Ready is not a prerequisite for reading last-good data. New live observations still require scoped gateway membership verification.

## Runtime and storage

Cloud absent: no task/timer/requests. Cloud present: bounded tracked actor and bounded channel; controller retains DriverCtx. Source setup/failure must be independent: local missing-token/cert/offline cannot park cloud; slow cloud/auth/quota cannot block local polling/preflight/deadlines. Preserve every native guard, pin-before-token, no replay, cancellation and semantic invariant. Reconcile source-owned IDs only; local refresh/preflight must never remove cloud summary. Bootstrap ownership after supervisor restart. Before ctx.ready(), explicitly keep sources not refreshed offline so held-offline restoration cannot resurrect stale data. Aggregate warnings so one recovered source does not clear another's failure. Stop/cancel joins or aborts workers, disables closed-channel select branches, and leaves no task behind.

Default inventory refresh1800seconds, with owner-requested manual refresh through local pending request. Automatic retries obey Retry-After (seconds or valid HTTP-date), otherwise bounded backoff60..3600seconds; unsupported collections stay qualified separately. Requests10seconds each; a cycle at most90seconds. Sequential reads, no unbounded fanout. Store snapshot once per completed cycle, preserving per-collection times/status; disk failure is visible and cached content never falsely fresh. Catalog+status endpoint reports stale runtime state and last observation. Session persistence acknowledged through controller before network progression. Existing secrets commit uses labels::write_atomic, which only writes/renames and does not fsync. Task3 must make secret transactions cancellation-safe and acknowledge only after file sync + atomic rename + parent-directory sync on supported Unix storage, propagating errors. Keep the same-process write lock alive until an offloaded transaction finishes even if its async caller is cancelled; update the in-memory map inside that completed transaction. Add meaningful cancellation/concurrency and failed-persistence tests. This is a narrow vault correction required by rotation checkpoint semantics, not a global labels/IO redesign or a claim of physical power-cut testing. UI/api work must not introduce network requests in cached GET.

## API/UI

New overkiz integration module, reuse people_api::is_owner (owner account/Access; PIN fallback only when no owners). Authenticate before cloning any vault data. Verify instance is configured kindoverkiz with cloud enabled. Fixed snapshot/status/pending keys only. Owner status GET, cached catalog GET, bounded onboarding/manual-refresh local POST. API only queues requests; no second token writer. Unknown/non-owner403 does not repeatedly prompt PIN; existing /api/session owner/human informs UI. API returns no auth credentials or raw upstream errors, global no-store applies.

Systeme optional Somfy panel for configured overkiz cloud instances: login, explicit site/gateway selection, status, per-collection availability and observation date, read-only list/expandable definitions, manual refresh and optional JSON download. Load full definitions only on demand, no localStorage, Svelte escaped text only. A catalogue response may expose a SHA-256 revision of its persisted catalogue bytes, using existing ring. For lossless on-demand details, an owner-only cached GET /api/integrations/overkiz-cloud/{instance}/definitions/{collection}/{index}?revision=... returns the selected raw definition serialized by Rust as JSON text. The same auth, binding, bounds and no-upstream-call helper applies. A changed revision returns409 rather than showing a different reordered definition. UI renders response.text() as escaped text; it never stringifies JSON-parsed numeric data for details/download. Full export keeps original catalogue-response bytes. No custom frontend JSON parser or new dependency is needed. No execution/activate/import buttons. All text FR/EN from shared catalogues. A preparation guide/config can create cloud-only observation instance; don't mutate household equipment or production HA. An isolated trial may be prepared after tests without replacing existing pilot.
